# 阶段 9：真实在线样本的更新审计

2026-10-16，`eagle3&dflash` 工作树。此阶段审计阶段 8 的旧训练方案：
BF16 参数和 AdamW 一、二阶矩、学习率 1e-5、首拒绝位置 ×2 的 KL、全量窗口。
随后用户授权减少训练数据、增加更新频率和采用位置衰减 KL；这些改动见阶段 10。

## 方法与可复现数据

Qwen3-8B + Qwen3-8B-DFlash-b16，AIME 2026 前四题，thinking/greedy，
最大输出 4096、上下文 8192，target/draft FULL graph，16 个训练核。
capture 后台保存每题前 768 轮已拥有独立 CPU 存储的 batch，包含原始特征、
完整 query、teacher、拒绝位置、step/source version。请求结束后才写磁盘。
还记录 CPU 训练起止和实际 GPU 安装时刻。此诊断请求的时间不能当作吞吐基准。

原始文件 `/tmp/dflash-update-audit/captures/request-{0..3}.pt`；
执行日志 `capture.log`、`legacy-audit.log`，目录同上。
完整每参数统计保存在 [update_audit_results.json](update_audit_results.json)。

CPU 从 W0 重放每题前四个实际训练窗口。每步比较相同窗口更新前后的 KL；
另取紧随窗口的 16 个真实 block，分别固定更新前 KV 和使用更新后的新增 KV。
旧历史 KV 均保留，不能把“新增段重投影”解释成全历史重建。
每次 optimizer 前保留参数并统计梯度，更新后统计发生数值变化的元素和 delta。
该额外扫描很昂贵，全部在脱离 GPU 的回放中执行，audit_train_seconds 不是线上训练耗时。

16 次 replayed_loss 与 capture 的 online_loss 一致，说明重放使用了相同窗口与缓存演进。
后续脚本默认已经改为新位置衰减 KL；本 JSON 保留旧方案原始结果，不能将新脚本
直接运行所得 loss 与旧 online_loss 的差解释成实现误差。

分母为 1,048,626,432 个可训练元素。norm 参数共 50,432 个，第一题每步仅
13 / 9 / 8 / 7 个发生数值变化。不能据此说所有未变化元素都没有梯度；
JSON 单独记录了梯度非零比例。BF16 直接更新会舍入小于有效间隔的改动，
且下一步没有 FP32 主权重来保留这些被舍入的余量。

16 次更新中，7 次连当前训练窗口的 KL 都未降低。未来 16 轮的 teacher top-1
匹配数在“更新后新增 KV”下，14 次不变，1 次少一个，1 次多一个。
这是已验证路径上的条件性代理指标，样本受原 proposal/拒绝位置截断影响，
不等于新 proposal 的真实接受率，也不能代表全数据集泛化。

## 结论及下一阶段

“更新次数少”有依据：大窗口越训越慢，CPU 完成的最后一次更新常来不及安装。
但审计表明单步更新本身也弱，不能只增加版本计数就宣布训练有效。
下一阶段分别改变位置权重、参与训练的 block 数和优化器精度，报告实际 GPU 安装次数、
生成/结束耗时、接受长度及输出一致性；FP32 主权重必须与同样采样设置的 BF16 对照。
训练 batch 变少不会允许漏掉历史特征、截断非因果 block 或改变真实安装分界。
